# Changelog

All notable changes, by release. Each pull request that changes something for
users describes it in a file of its own in `changelog.d/`, or under Unreleased. The
release bot makes that text the section of the next release, or lists the pull
requests when there is none.

## Unreleased

## [0.10.0](https://github.com/Dennis-Otto/repo-pager/compare/v0.9.1...v0.10.0) (2026-11-13)

### Features

- The pager can watch the repositories of an organization. Before, it served only the repositories of `MAINTAINER_LOGIN`, and the set-up registered the GitHub App only in a personal account, so someone whose repositories live in an organization learned only at the end of the set-up that nothing paged. Now the new variable `OWNERS` of `wrangler.jsonc` names organizations whose repositories the pager watches beside yours, separated by commas, and `node scripts/register-app.mjs "$WORKER" --org ORGANIZATION` registers the app in an organization. Who counts as you stays `MAINTAINER_LOGIN`, so what the other members of the organization open pages as a contribution. The README and the set-up guide say before the set-up which app and which control repository fit your accounts, and what an organization can't do yet. Without `OWNERS`, nothing changes; it needs no new permission and no new secret.
- The words below a photo, a file or a voice message now reach the control repository as a text does, with its 👀 and its answer: a screenshot sent into the topic of an issue with "is this the bug they mean?" is no longer dropped. Before, the pager read only the text of a message, which Telegram leaves empty for a photo or a file, so such a message got no reaction and no answer and looked like a dead pager. A photo, a file or a voice message without words now gets an answer in its thread at once, that the pager reads text only, and `/help` says so too. The picture, the file and the voice itself still stay in Telegram. It needs no new permission and no new secret.
- Write `/status` to the bot, and it tells you at once how your pager is, one line each: when its schedule last ran and the last failure that the runs since haven't got past, whether Telegram takes the bot and its webhook, whether GitHub takes the key of the app and whether the app is installed on your control repository, whether `GITHUB_USER_TOKEN` is set, and how many days each token has left. A line that fails names the step of the set-up guide that fixes it, so a new instance can check itself at step 6, before its control repository runs, and a quiet pager can be asked why without waiting for the daily check *Health* or opening Cloudflare. It only reads, names no secret, and `/help` mentions it. It needs no new permission and no new secret.
- The pager now follows a contribution past its first message also when the contributor answers a review or pushes the fix. Before, only a comment in the conversation reached it: a review of someone else, a reply in the thread of a review comment, new commits on a pull request, a reopened pull request or issue, and a draft made ready for review stayed silent, so a pull request waited unseen after you asked for changes. Now a review and a reply in a review thread come like a comment, quoted in the message with one notice in its topic, and new commits, a reopen and ready for review add a note such as *🔁 New commits by octocat.* with one notice; a thing that was done, such as after your request for changes on GitHub, opens again. Your own reviews end the wait for a reply as your comments do, and your pushes and those of bots mean nothing. Subscribe the app to the events *Pull request review* and *Pull request review comment* under *Permissions & events* in its settings; its permission *Pull requests* covers them, so no installation needs to accept anything.
- The pager now writes each moment of a message in your time zone. Before, *Failed on …* of a failing workflow and every other time came in UTC, so the hour was off and, near midnight, the day too. Set `TIME_ZONE` in `wrangler.jsonc` to a time zone such as `Europe/Berlin` or `America/New_York`; empty, it stays UTC, and a name that the Worker doesn't know is named among the settings that are wrong.
- The pager now notices when a release of its own didn't go live on Cloudflare. Before, Workers Builds deployed outside GitHub, and a build that only uploaded the release as a version without traffic, or one that never started, such as after a rename of the repository, showed only in the dashboard of Cloudflare: the release on GitHub said that a fix was out while the version before kept serving. Now the Worker knows its version, `/status` names it, and the health that the control repository asks for each day carries it as `version`, with `release`, the release of the pager that the Worker doesn't run yet. When the release of the pager's own repository still isn't live 30 minutes after GitHub published it, a message says so, once, with where to look. The pager hears of its releases when its app is installed on its own repository; it needs no new permission and no new secret.
- A text in the topic of a failing workflow can now end in a ✅ **Confirm** button. Before, a proposal of the control repository could name a contribution, an alarm, a security message or a release, but not the failing workflow, the red thing that the pager shows most often, so *run it again* or *ignore it* written there got an answer without a button. Now a proposal names a failing workflow by its file, and 🔁 **Rerun** and ✖ **Ignore** come with their button while the workflow offers them; a text in its topic tells the control repository the file as `path`. A control repository whose template doesn't know the new kind yet keeps working as before.
- A thing that you ignored can come back. Before, ✖ **Ignore** acted at once and left the message without a button, so a press that slipped beside ⏰ **Later** hid an issue and every later comment of its author for 30 days, or muted a workflow that fails on `main`, and the only repair was to remember it and look at GitHub. Now an ignored thing offers ↩️ **Bring back**, which opens it again, in place, as it was when you ignored it: its buttons come back, its topic loses ✅, and it no longer expires. A thing that waited for a draft, a fix or a rerun comes back with the button that starts one again. What happened on GitHub while it was ignored, such as a comment, shows with its next event, and an issue, a pull request or a discussion that ended there meanwhile comes back done. The button comes with what you ignore from this release on: the message of a thing ignored before keeps no button. It needs no new permission and no new secret.
- Write `/open` to the bot, and it lists what still waits for you, in one message: each thing that is open and still offers a button, grouped by repository, linked to its page on GitHub, with when ⏰ **Later** brings it back. Done and ignored things stay out, and with nothing open it says so in one line. Before, the topics of the chat were the only overview, where done, ignored and open things stand side by side. It only reads, acts on nothing and sends nothing to the control repository; `/help` mentions it, and the set-up guide shows how to register `/open`, `/status` and `/help` in the menu of Telegram. It needs no new permission and no new secret.

### Changes

- The README and the setup say what a watched repository needs: which messages work anywhere, and which need release-please, the release workflows, the visual check, the bot-health bot or the issue assistant of repo-blueprint.
- The home page of the website names all three tokens whose expiry the pager reminds you of, the redelivery of failed events and the daily health check.

### Bug fixes

- A failed release now stays in the alarm until the pass that takes it up. Before, any later green run of the release workflow took its entry out and turned the alarm ✅, also the run of the next push or of the morning's schedule that found nothing to release, while the release that failed was still an unpublished draft. Now a later attempt of the run that failed, such as one of 🔁 **Rerun**, and a run of the release workflow started by hand take the entry out, and any other green run takes it out only once none of the ten newest releases of the repository is a draft any more. It needs no new permission and no new secret: the pager reads the releases with the permission of the app to write the contents, which it has already, since GitHub lists drafts only to such a token.
- The reminder of a token that expires now says what is true when it shows. Before, it was written once, three weeks before the day, and never again: ⏰ **Later** brought it back with "expires in 21 days" also two days before the day, and on the day itself no message came for the token of Claude or `PAGER_FIX_TOKEN`, since their reminder of that day already existed. Now a reminder that comes back counts the days that are left then, and on the day a token expires a new message notifies you that it has expired, whether the first reminder is still open, put aside by ⏰ **Later**, or closed by ✅ **Renewed** while the day stayed the same. A token renewed with a new day gets its own reminders, as before, and a reminder of its old day that ⏰ **Later** put aside closes quietly when it comes back, rather than saying that the token expired. It needs no new permission and no new secret.
- The reply to every prompt of ✏️ **Edit** now becomes the new draft of its own thing. Before, the pager remembered only the latest prompt: after ✏️ Edit on a second draft, or on the same draft again, the reply to the earlier prompt went to the control repository as a question, which cost a run of Claude and an answer that nobody asked for, while that draft stayed as it was and its prompt stayed in the chat. Now each prompt waits a day for its reply, apart from the others. A prompt that is still open while you update the pager no longer finds its draft: press ✏️ Edit once more. It needs no new permission and no new secret.
- An event of GitHub that the pager failed to handle is now delivered again, or shown in the alarm, also on a busy day, such as during a rollout over many repositories. Before, the schedule looked only at the 300 newest deliveries of the app, which hundreds of workflow runs fill within one quarter of an hour, so a failed event behind them was lost without a sign. Now each run reads the failures of the last three hours on a list of their own, and the other deliveries back to the run before, and the log of the Worker says when it can't read back as far as it should.
- A button that acted on GitHub now acts once, also when Telegram fails right after. Before, the pager saved what a press did only once Telegram took the change of the message: when Telegram answered with an error, such as in an outage or with a 429 that asks to wait long, the reply was posted, the fix started or the release merged on GitHub, but the message kept its buttons, the press got no answer, and a second press of ✅ **Send** posted the same reply in a discussion again, or 🛠 **Start fix** started a second run of Claude. Now the new state is kept as soon as GitHub has acted, the press gets its answer, a second press is refused as out of date, and the next change of the thing shows the right message. This holds for ✅ **Send**, 🛠 **Start fix**, ✍️ **Draft a reply**, 🔀 **Merge**, 🤖 **Assistant again**, 🔁 **Rerun** and the answer to a question of an agent. It needs no new permission and no new secret.
- One thing that Telegram or GitHub refuses in a run of the schedule, such as a message that is too long, no longer stops the rest of the run. Before, the first such error ended every run at the same thing for as long as it kept failing, so the events of GitHub that failed were not delivered again, and the reminders and the renames of topics waited. Now each thing goes on its own: the one that failed goes to the log and comes again in the next run, and the others, the later steps and the redeliveries still run. The schedule shows only as many things as the calls of a run allow, so a run with many things due no longer stops in the middle of one, and a thing whose new message went out stays at that message, also when the delete of its old message fails, rather than coming again with live buttons on both. The answer to the check of the pager's health names the last thing that failed, as `failure`.
- The tests of a copy now pass with its own values in `wrangler.jsonc`. Before, some tests held on to the maintainer, the control repository and the language of the maintainer's own instance, so a copy that set its own, as the set-up guide asks, failed its required check *check (node)* and couldn't merge a change of its own or take an update through a green pull request. Now the tests take these values from `wrangler.jsonc`, and `bash scripts/check.sh` runs them once more with those of another instance, so that such a test can't come back. The Worker itself is unchanged.
- `node scripts/register-app.mjs` no longer creates the GitHub App when Wrangler couldn't store its secrets. GitHub hands out the private key and the webhook secret of a new app only once, and before, a Wrangler that wasn't signed in or a Worker that wasn't deployed yet left an app on GitHub whose key was lost, with only `wrangler secret put NAME failed` to go on. Now the script checks with `wrangler secret list` that Wrangler reaches the Worker before it sends the manifest to GitHub, and stops with what to do when it can't. Should a secret still fail to reach the Worker, it names the secrets that are stored and those that are missing, and the page of the app's settings where you make a new private key and set a new webhook secret, or delete the app and run the script again.
- A free text of more than 4000 characters, such as a pasted log, now gets an answer in its thread at once that says how long it is and what the control repository takes, and goes nowhere. Before, the pager sent it, the control repository refused it in a run that failed red, and the text showed 👀 for an hour and then 😢 without a reason. 🛠 Start fix now sends only the entries of its repository, each label cut to 300 characters, so a failed event of GitHub in the same alarm, or an alert with a long description, no longer makes the control repository refuse the whole fix and leave the thing in *fixing* for an hour.
- Every button press now gets an answer, and every text a reaction. Before, a press whose handling failed in a way the pager didn't expect, such as when Telegram refused the change of the message with a 5xx before GitHub was asked, or a write of Workers KV failed, left the button in Telegram's loading state until Telegram gave up, and nothing told you whether it had acted. Now such a press gets the alert *😢 The pager failed on this press, and whether it acted is uncertain*: look at the thing on GitHub, then press again. A free text that GitHub refused to pass to the control repository, such as when the app may no longer dispatch there, now gets 😢 and a message in its thread with GitHub's reason, and a text whose handling failed otherwise gets 😢 and a message that the pager failed on it, instead of no answer at all. The error still goes to the log of the Worker. It needs no new permission and no new secret.
- A new failure or security alert that joins an open bundle of its repository now notifies you. Before, only the message that opened the alarm or the security message rang; every entry after that only edited it, and an edit in Telegram notifies nobody, so a failed release, a broken required check, a high alert of code scanning or a leaked secret came without a sound whenever the bundle already held an entry. Now the message still lists the new entry in place, and a short message below it in its thread, *🚨 New in this alarm* or *🛡 New in this security message*, notifies. The new entries of ten minutes after a notice of the bundle, such as a push that breaks a few checks at once or the alerts of a new query of code scanning, notify once, an entry that fails again only edits the message, as before, and a bundle that ⏰ **Later** put aside comes back at once with a new entry. A comment on an issue or a pull request whose thing moves from the main chat into its thread with it now notifies as well. It needs no new permission and no new secret.
- A pull request of someone else from a fork now pages when it opens, also when its branch is named like one of release-please, such as `release-please--branches--main`, which a fork that runs release-please gets by itself and anyone can choose. Before, the pager took every such pull request for a release and stayed quiet: it came without a message and without a draft, its end didn't tick its thing off, and new commits on it brought no news. Now only a branch of release-please of the repository itself makes a release, and every other pull request is a contribution like any other. It needs no new permission and no new secret.
- A high or critical alert of code scanning that was found first in a pull request now pages once the merge brings it to the default branch. GitHub creates such an alert on the branch of the pull request and, after the merge, says only that it appeared on the default branch, which the pager ignored, so the most usual way of a severe alert onto the default branch, a merged pull request, came without a message. An alert that someone dismissed stays quiet, and an alert that paged already isn't listed twice. It needs no new permission and no new secret.
- The website shows the mark of Repo Pager, the speech bubble with a bell of its social preview, as the logo in its header and as the icon of its tab, in place of the stock icon of its theme.
- 🤖 **Assistant again** now starts the issue assistant on the default branch of the repository. Before, it always asked GitHub for `main`, so in a repository whose default branch has another name nothing started, and the button said that the issue assistant didn't take the override yet, which was wrong: every refusal of GitHub other than an unknown input `override` now shows GitHub's own reason.
- The set-up guide no longer leaves the webhook of Telegram without its secret. Its commands kept the token of the bot, the address of the Worker and the random secrets in variables of the shell without saying so, and in a new shell step 5 set the webhook without the secret, so the Worker refused every update. The guide now says to run every step in the same shell, reads the token of the bot in a step of its own, and each command that needs a variable stops with what to do when it is empty, with how to make a random secret anew. It also says to delete `.github/dependabot.yml` of a new control repository, as its template asks, and that a copy of the pager needs none of the workflows that it brings along.
- 🤖 Assistant again in a repository without the issue assistant, or one that `GITHUB_USER_TOKEN` can't see, now answers *… has no issue assistant … Nothing was started.* instead of a bare *GitHub refused: Not Found*.
- The German website has the page *Releases und Cloudflare*, which its guide of the setup links at the step that creates the Worker, German names in its whole menu, a German description for the previews of its links, and says at the links of the architecture and the security design that they are English.
- A call to Telegram or GitHub that hangs no longer holds up the pager. Before, no call had a time limit, and since the pager handles one change after the other, one slow answer kept every event of GitHub, every press of a button and the schedule waiting behind it: the events ran past GitHub's ten seconds and failed, and a button showed its loading state with no answer. Now each call ends after five seconds, with the reading of its answer, and the download of the artifact of a visual check after twenty. An event whose call ends there answers `500` and comes again, and a button answers *⏳ GitHub gave no answer in time, and whether it acted is uncertain*, so that you look on GitHub before you press again; an answer you wrote to an agent's question says the same of its save. It needs no new permission and no new secret.
- The pager now checks on its own that a translated line of the notes of a release adds no link. Before, it kept a line from the control repository when it kept the references and names of code of its English line, also when it added a URL, a host such as `example.com`, an address of e-mail, an `@name` or a `/command`, which Telegram links by itself, and relied on the check of the control repository to refuse such a line. Now such a line shows its English, as a line that lost a reference does, with the same rule as the control repository's.
- A workflow whose rerun from 🔁 Rerun is cancelled, by hand or by the concurrency group of its workflow, no longer stays at *🔁 The failed jobs run again…* without a button until some later run of it ends: its message fails again, edited in place, with 🔁 Rerun back and the note *⏹ The rerun was cancelled.*
- A thing that ends while ⏰ Later has put it aside, such as an issue closed on GitHub, an alarm whose last entry turned green or a release merged on GitHub, no longer keeps the line *⏰ Back in N h* in its finished message, and a release merged within the hours of Later no longer comes back as a new message that notifies. A release that an update takes back to ready still keeps its Later.
- The album of a visual change no longer shows an animation as three pictures that don't fit together. Before, it showed the changed pixels of one frame, such as step 4, beside the first frame of the animation before and after, so the change looked like another picture. Now each changed picture comes as one photo, the place of its change before and after of the same frame with the changes framed in red, captioned with how much it changed and, for an animation, the frame, such as *frame 4 of 7*; this needs the visual check of the next release of the blueprint. With an older visual check, an animation shows its changed pixels alone, captioned as one frame of the animation. With one photo per picture, an album now holds up to ten changed pictures.

## [0.9.1](https://github.com/Dennis-Otto/repo-pager/compare/v0.9.0...v0.9.1) (2026-11-10)

### Bug fixes

- A red workflow on `main`, and any other thing whose topic Telegram refused, now shows in its own thread once Telegram opens threads again. Since 9 November 2026 Telegram refuses every new thread of a bot's private chat (`BOT_TOPIC_WRONG_HOME`, [tdlib/telegram-bot-api#944](https://github.com/tdlib/telegram-bot-api/issues/944)) and still posts *"…" was created* in the main chat, with no thread behind it: the message then had to go into the main chat, and stayed there. Now an open thing that waits there moves into a thread of its own with its next change, such as the next failed run of its workflow, quietly, and its message in the main chat is deleted; Telegram deletes no message older than 48 hours, so such a one only loses its buttons there and shows the thing as it is now. While Telegram refuses threads, the pager asks for none for an hour, then two, then four, so an outage no longer leaves a notice of a thread that isn't there with each message; a passing error of Telegram, such as a 5xx, pauses nothing. A done thing stays where it is. It needs no new permission and no new secret.

## [0.8.0](https://github.com/Dennis-Otto/repo-pager/compare/v0.7.0...v0.8.0) (2026-11-08)

### Features

- Dennis Otto Pager is now **Repo Pager**, a pager that anyone runs for their own repositories. The repository is [Dennis-Otto/repo-pager](https://github.com/Dennis-Otto/repo-pager) and the website <https://dennis-otto.github.io/repo-pager/>, and the old addresses of the repository lead there. [Set up](https://dennis-otto.github.io/repo-pager/setup.html) starts with your own copy, says what to set in its `wrangler.jsonc`, and why there is no shared app to install: your tokens and the events of your repositories stay yours, each pager serves the one chat of its maintainer, and your own subscription of Claude answers. A new GitHub App of the pager is called *Repo Pager*, which you change to a name of your own when you confirm it. A pager that runs needs no change: it keeps its Worker, its address, its secrets, its state and its GitHub App.

### Bug fixes

- A message about a thing whose topic you deleted opens a new topic instead of landing in the main chat. That holds for every message of the thing: its own message when it changes or ⏰ Later brings it back, and the messages below it, such as the pictures of a release and their album, the notice of a new comment, a draft to read or a proposal with ✅ Confirm, which bring the thing's own message with its buttons into the new topic first. The thing keeps the new topic, so its later messages follow there. A thing that an earlier version left in the main chat after you deleted its topic, such as a release whose pictures kept landing there, moves into a new topic with its next message. The main chat is left for a chat without topics, for a topic that Telegram refuses, and for a thing from before topics, and a comment whose message went anew no longer notifies twice. It needs no new permission and no new secret.

## [0.7.0](https://github.com/Dennis-Otto/dennis-otto-pager/compare/v0.6.0...v0.7.0) (2026-11-08)

### Features

- The pager follows the comments of an issue or a pull request of someone else. A new comment of someone else edits the message of its thing to name the comment, and one notice in its topic tells you, once for a few quick comments; a draft that you asked for is written again for the comment, and your own text with ✏️ Edit stays your draft. Once its reply went, the thing opens again with ✍️ Draft a reply, and an issue from before the pager comes as a new thing. Your own comment on GitHub, and the issue or the pull request closed or merged, make the thing done, without buttons, so ✅ Send can't post a second answer. The comments need the event *Issue comment*, which you tick in the settings of the app.
- A message shows what its thing says, so you rarely need to open GitHub. A new issue, pull request, discussion or comment quotes the first 500 characters of its text as a folded quote, without the hidden hints of its form. A release shows its notes from its pull request: the headings in bold, each item with its pull request linked, 15 lines at most and *… and N more* for the rest, and *⚠️ Breaking changes* above them when the notes name breaking changes or the major version goes up from 1 or above, so you know what 🔀 Merge publishes. Notes changed on the pull request show in the message too.
- An event of GitHub that the pager failed to handle, such as in a short outage of Telegram, comes again by itself: GitHub never delivers a failed webhook again on its own, so every 15 minutes the pager has it delivered again, three attempts in all. An event whose attempts all fail shows once in the alarm of the control repository, *🚨 An event of GitHub fails: pull_request.opened*, with a link to the recent deliveries on the app's Advanced page, and an attempt that passes later takes it out. A discussion or a comment that comes twice no longer sends its message again or asks for a second draft. An event that a newer one of its kind in the same repository has overtaken, such as a failed run before a rerun that passed, doesn't come again, so a late copy can't bring back an older state; a short wait that Telegram asks for in a burst of messages is honoured once; and an alarm of such events offers no 🛠 Start fix. It needs no new permission and no new secret.
- The pager tells you of a private vulnerability report and of a secret that secret scanning found, which GitHub announced only by mail. A report gets a message of its own, *🔐 Vulnerability report in demo*, with its severity, its link and the days by which `SECURITY.md` promises to acknowledge and to assess it, and ⏰ Later and ✖ Ignore; what the report says stays on GitHub while it is under embargo, so no message, record or log of the pager names its summary or its description. On the day before its acknowledgement is due, a report that still waits in triage comes again, once, and its advisory published ticks it ✅. A secret is an entry of the security message of its repository, which is what the message of code scanning is called now, *🛡 Security in demo*: the kind of the secret and its file, such as *🔑 Mailchimp API Key in config/.env*, never the secret, and *leaked in public too* when GitHub found it in public; resolved takes it out. The app needs the permissions *Repository security advisories: Read* and *Secret scanning alerts: Read* and the events *Repository advisory* and *Secret scanning alert*, which you give it in the settings of the app, as the setup says.
- The pager tells you before it breaks. Three weeks before `GITHUB_USER_TOKEN` of ✅ Send and 🤖 Assistant again expires, a 🔔 reminder in a topic of its own names the day and how to renew it: the pager reads the day from GitHub once a day, so no setting names it, and a token that GitHub refuses, because it expired or was revoked, gets a reminder too. The same reminder comes for `PAGER_FIX_TOKEN` of 🛠 Start fix, whose day the daily check of the control repository sends along. ✅ Send and 🤖 Assistant again say that GitHub refuses the token, instead of a bare refusal. The control repository can now ask the pager for its health with the signed body `{"type": "health"}`: when its schedule last ran, whether Telegram takes the bot and delivers its webhook, whether GitHub takes the app, and the days of the tokens, without a secret; its daily check fails, which GitHub notifies by itself, when one of them is wrong. It needs no new permission and no new secret.
- Any workflow that fails on `main` pages you once, not as a mail of GitHub per run: a push, a schedule, a bot such as *Findings* or *After the checks*, or a start by hand. Its message, such as *🔴 Docs fails on main in Dennis-Otto/player-switch-for-autodarts*, names the jobs that failed, each linked to its log, and offers 🔁 **Rerun** of the failed jobs and ✖ **Ignore**. Each run that fails again edits it in place, with how often and when, without a notification, and a run that passes the jobs that failed turns it ✅. A first attempt waits ten minutes for the rerun that *After the checks* makes of the tests and of a release, so a rerun that passes never pages. A required job of GitHub Actions now pages as its workflow, and an issue of the bot-health bot as the run that it names, so the same failure no longer pages twice. With this, you can turn off the mails of GitHub Actions in your notification settings; keep *Web and Mobile* on, or keep the mails of the control repository with a filter, since the failed *Health* run of a broken pager reaches you only that way. It needs no new permission and no new event of the app.
